Git — это программа для отслеживания изменений в коде на вашем компьютере, а GitHub — это сайт и облачный сервис для хранения этого кода и командной работы

git status
Отображает общую сводку по проекту. Показывает текущую ветку. Перечисляет файлы, которые были изменены в рабочей директории, но еще не подготовлены к коммиту. Показывает файлы, добавленные в область подготовки (индекс), которые войдут в следующий коммит. Выводит подсказки о том, какие команды можно ввести дальше.

git diff
Сравнивает содержимое рабочей директории с областью индекса. Показывает неиндексированные изменения — то есть конкретные построчные правки, которые вы внесли в файлы после последнего сохранения, но еще не вызвали для них git add. Если запустить просто git diff, вы увидите разницу во всех измененных файлах проекта.

git diff --staged (или git diff --cached)
Сравнивает проиндексированные изменения с последним коммитом. Показывает то, что уже подготовлено с помощью команды git add и готово отправиться в репозиторий при следующем вызове git commit. Позволяет еще раз проверить свои файлы перед созданием коммита.

Ветка в Git — это указатель на один из коммитов, который представляет собой отдельную линию разработки проекта. По сути, это просто текстовый файл, в котором записан хэш-код конкретного снимка вашей работы, что позволяет изолированно разрабатывать новые функции или исправлять ошибки, не затрагивая основной код.
Когда вы делаете новый коммит, ветка, на которой вы сейчас находитесь, автоматически передвигается вперед. Git создает новый снимок проекта, связывает его с предыдущим коммитом и перемещает указатель текущей ветки на этот свежий коммит. Таким образом, ветка всегда указывает на самую последнюю сохраненную версию в этой линии разработки.
Слияние, или мерж, объединяет изменения из одной ветки в другую. Git берет общую начальную точку двух веток, сравнивает изменения, сделанные в них независимо друг от друга, и совмещает их. Если файлы менялись в разных местах, Git автоматически объединяет код и создает специальный коммит слияния, после чего целевая ветка начинает содержать в себе все наработки из присоединенной ветки. Если же в одной и той же строчке файла были сделаны разные изменения, возникает конфликт слияния, который разработчик должен разрешить вручную.





Главное отличие между git diff, git show и git log заключается в их назначении: git diff сравнивает разные состояния кода (построчно), git show отображает содержимое конкретного объекта (обычно коммита), а git log выводит хронологическую историю коммитов. Опция git log -S находит коммиты, в которых определенная строка была добавлена или удалена, а git blame показывает автора и коммит для каждой отдельной строки в конкретном файле.



Разница между git diff, git show и git log

git diff показывает разницу (изменения) построчно между двумя состояниями. Чаще всего используется, чтобы посмотреть, что вы изменили в коде прямо сейчас, но еще не закоммитили (git diff), или сравнить две ветки/коммита.

git show показывает детали конкретного объекта (коммита, тега). Чаще всего используется, чтобы заглянуть внутрь конкретного коммита: увидеть его автора, дату, сообщение и весь список измененных в нем файлов с их кодом.

git log показывает список (историю) коммитов. Чаще всего используется, чтобы понять хронологию проекта: кто, когда и зачем делал коммиты в этой ветке. Сами изменения в коде по умолчанию не выводятся.



Что именно нашли git log -S и git blame?

git log -S "строка_поиска" (Поиск по истории изменений)
Этот флаг ищет моменты изменения количества упоминаний указанной строки. Он выведет список коммитов, в которых искомая строка появилась впервые или была полностью удалена (то есть изменилось общее число её вхождений в файл).
Пример использования: Вы помните, что в коде когда-то использовалась функция calculateTax(), но сейчас её нет. Команда git log -S "calculateTax()" покажет коммит, в котором эту функцию внедрили, и коммит, в котором её стерли.

git blame путь_к_файлу (Построчный анализ текущего файла)
Эта команда буквально переводится как "обвинить". Она берет текущую версию файла и раскладывает её построчно. Для каждой строки в файле она показывает хэш последнего коммита, который затронул эту строку, имя автора, который этот коммит сделал, а также дату и время изменения.
Пример использования: Вы нашли баг в строке 42 файла index.js. Вы запускаете git blame index.js и видите, кто именно и в каком коммите последним редактировал эту строку.



Разница между git restore и git restore --source=... 
заключается в том, откуда именно берутся данные для восстановления файла.

Команда git restore <файл> восстанавливает файл в рабочей директории из индекса. Если в индексе изменений нет, то берется состояние из последнего коммита (HEAD). Она используется, чтобы просто отменить текущие незакоммиченные правки.

Команда git restore --source=<указатель> <файл> берет версию файла из конкретного места в истории — например, из коммита, который был два шага назад (--source=HEAD~2). Она не просто отменяет текущие правки, а заменяет файл его старой исторической копией.

Что произошло с моими правками:
При выполнении первой команды (git restore) ваши локальные изменения — удаленные строки — были бы безвозвратно стерты. Поскольку эти правки не сохранялись ни в индекс, ни в коммит, Git никак не смог бы их вернуть. Файл просто вернулся бы к чистому состоянию последнего коммита. При выполнении второй команды с флагом --source ваши текущие правки также перезаписались бы старой версией из указанного коммита.



Чем git revert отличается от git reset --hard:

Команда git revert HEAD создает новый коммит, который вносит строго противоположные изменения по сравнению с ошибочным коммитом. При этом сама ошибка и вся история проекта остаются нетронутыми — они просто перекрываются новым «исправляющим» коммитом.

Команда git reset --hard физически стирает коммиты из истории, возвращая указатель ветки назад. Все изменения в рабочей директории и индексе после указанного коммита полностью уничтожаются.

Git revert безопасен, потому что он работает исключительно «вперед». Он просто добавляет новый коммит в общий поток. История остается последовательной, ни у кого из коллег не возникнет сбоев при синхронизации, а ошибочный код и процесс его исправления будут прозрачно видны в логах.
